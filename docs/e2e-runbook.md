# E2E runbook

This runbook drives either the canonical Docker Desktop Kubernetes deployment
or the legacy Compose alternative through the Postman/Newman collection
generated by `scripts/generate_postman_collection.py`.

For a step-by-step guide including a manual curl walkthrough of the order saga,
see `docs/self-run-guide.md`.

## Canonical Kubernetes execution

- Deploy the full local platform with `docs/self-run-guide.md`.
- Confirm `kubectl config current-context` is `docker-desktop`.
- Node.js (only needed to run `newman`; `scripts/newman.sh` falls back to
  `npx newman` automatically if `newman` isn't installed globally).

Run:

```bash
./scripts/local-k8s-test.sh
```

The script waits for all 12 Deployments, initializes Kafka topics, creates a
temporary gateway port-forward on `localhost:18080`, and runs Newman against
that private endpoint. It stops the port-forward on exit.

## Legacy Compose execution

Start the optional full-fleet Compose environment, then run:

```bash
./scripts/event-smoke.sh
./scripts/e2e-test.sh http://localhost:8080
```

`smoke-test.sh` and `e2e-test.sh` are Compose-aware: they check host-mapped
Actuator ports and can fall back to `docker exec`. Do not use them as the
Kubernetes health check.

If `scripts/generate_postman_collection.py` changes, regenerate the checked-in
collection before either path:

```bash
python3 scripts/generate_postman_collection.py
```

`scripts/newman.sh` includes a request delay because bounded polling waits for
the asynchronous outbox/Kafka choreography to complete.
The Happy Path's `Poll Until CONFIRMED` step also waits one second before each
retry in its pre-request script. Run the Happy Path in **Collection Runner**
(not by repeatedly clicking Send); no Runner delay setting is required for
that step. Its 30 bounded retries allow at least 30 seconds for the saga,
and a non-200 response or cancelled order fails immediately.

The latest recorded full local Kubernetes run completed **193/193
assertions**; request count varies with bounded asynchronous polling. This is
a recorded validation result, not a guarantee that an unstarted or modified
environment is currently healthy.

## Bugs found and fixed via this E2E work

- **api-gateway PUT/PATCH routing** - certain routes only forwarded GET/POST.
- **Idempotency-Key** header validation on order creation (400 when missing).
- **Prescription activation RBAC** - only PHARMACIST/ADMIN may activate.
- **api-gateway medications route method whitelist** was too narrow.
- **MySQL TIMESTAMP 2038 ceiling** - switched affected columns off `TIMESTAMP`.
- **notification-service compose.yml DB config** was pointing at the wrong
  schema/credentials.
- **notification-service Hibernate UUID JDBC type mismatch** with MySQL.
- **notification-service & payment-service JWT claim bug**: both read a
  non-existent `userId` claim (`NullPointerException`) instead of the
  standard `sub` claim that auth-service actually issues (containing the
  user's UUID). Fixed both to read `sub`, matching the established pattern in
  `customer-service.CustomerController.extractUserId()`.
- **notification-service missing `JwtAuthenticationConverter`**: with no
  converter bean, Spring Security's default authority mapping looks for a
  `scope`/`scp` claim, not this platform's custom `roles` claim - so every
  `hasRole(...)` check silently failed (isAuthenticated() checks still
  passed). Added the same converter bean pattern used by every other service.
- **audit-service `@Secured` RBAC gap (significant)**: `AuditController` used
  `@Secured("ROLE_ADMIN")`, but `@EnableMethodSecurity` only enables
  `@PreAuthorize`/`@PostAuthorize` by default (`securedEnabled` defaults to
  `false`). Every `@Secured`-protected audit-service endpoint had been open to
  **any authenticated user regardless of role** since the code was written.
  Fixed by switching to `@PreAuthorize("hasRole('ADMIN')")`, matching the
  dominant convention used everywhere else in the codebase.
- **inventory-service duplicate stock level**: creating a stock level for an
  already-existing `(pharmacyId, productId)` pair threw an unhandled
  `DataIntegrityViolationException` (generic 500). Added a pre-check,
  `StockLevelAlreadyExistsException`, and a 409 CONFLICT mapping.
- **notification-service mail health indicator**: no SMTP server is
  provisioned locally, so Spring Boot's auto-configured mail health indicator
  always reported `DOWN` (connection refused), dragging down the whole
  liveness/readiness aggregate even though the service itself was fully
  functional. Disabled via `management.health.mail.enabled: false`.
- **audit-service event ingestion**: the Kafka consumers required the common
  envelope while order, inventory and payment producers emitted flat payloads.
  The consumers were also never bound because `spring.cloud.function.definition`
  was unset, and their `JsonDeserializer` expected type headers that these
  producers do not send. Audit ingestion now explicitly binds every
  contract-defined topic, uses `StringDeserializer`, accepts the documented
  envelope and normalizes existing flat order/inventory/payment payloads.
  Inbox insertion and audit-row creation share a transaction, duplicate events
  are ignored, and malformed events propagate through bounded retries to the
  topic's `.dlt` instead of being swallowed.
- **payment ownership checks**: comparing JWT `sub` directly with
  `payment.customerId` compared unrelated user/customer IDs. Payment reads and
  direct payment creation now forward the caller's JWT to customer-service's
  existing owner-protected profile endpoint; staff roles remain permitted.
  Payment creation also validates that the requested customer owns the order
  and rejects idempotency keys reused for a different customer/order. A
  customer-service outage returns a sanitized 503 rather than bypassing or
  silently denying the ownership check.
- **Postman/Newman `setNextRequest` global name collision**: two different
  scenarios each had a bounded-polling step literally named
  `"3. Poll Until CANCELLED_PAYMENT (bounded)"`. Postman resolves
  `setNextRequest` by name **globally across the whole collection**, not
  scoped to the current folder, so one scenario's self-referencing polling
  loop could hijack the other's steps entirely. Renamed both to unique names.
- **`PaymentStatus` enum correction**: the collection asserted a status value
  of `AUTHORIZED`, which does not exist (`PENDING/PROCESSING/SUCCESS/FAILED/
  REFUNDED`). Fixed the assertion and the step name.
- **Test-design fixes** (not app bugs): isolated the "insufficient stock"
  scenario onto a dedicated fixture instead of the shared `medicationId` (used
  by nearly every other order test) to avoid starving unrelated scenarios;
  widened a couple of assertions that varied between 400/404/409 depending on
  timing; fixed an RBAC negative test that was sending a bean-validation
  -failing payload, which masked the intended 403 behind Spring MVC's
  argument-resolution-before-`@PreAuthorize` ordering (validation errors
  surface as 400 before the authorization check ever runs).

## Resolved gaps

- **Notification ownership**: `GET /api/v1/notifications` now requires a
  `customerId` filter, and notification reads/updates authorize customers by
  asking customer-service whether the caller owns that customer profile (staff
  roles bypass the lookup). The happy-path Newman step now polls, with a bounded
  wait, for a `SENT` notification instead of logging a best-effort warning.
- **Event-driven notifications**: notification-service now consumes order,
  payment and prescription topics with per-topic consumer groups, keeps an
  order-to-customer projection from `OrderCreated`, retries payment events
  until that projection exists, and dead-letters to `<topic>.dlt`. Email is
  simulated by default (`NOTIFICATION_EMAIL_MODE=simulated`).
- **Audit Kafka headers**: correlation headers arrive as `byte[]`; audit now
  decodes them via `CorrelationIdContext.fromHeader`, and DLQ bindings use
  `dlqPartitions: 1` to match the single-partition DLTs.
- **Saga polling**: bounded polls were raised to 30 attempts because three
  outbox hops at a 5 s interval take 11-15 s.
- **`StockLevelTest.testCreateStockLevel`**: now expects a `null` version for a
  new entity, matching the documented Spring Data `isNew()` behavior.

## Known environment quirks (not application bugs)

- Occasionally, after several `docker restart` cycles during iterative
  development, a container's host port mapping can desync (host connections
  get reset even though the service is fully healthy internally and reachable
  through the gateway). `scripts/smoke-test.sh` automatically falls back to
  `docker exec ... curl` per-service when this happens, so it does not cause a
  false failure.
